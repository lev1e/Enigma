### Root cause of the mass refusal (found, partly fixed)
`formats._anonymize_image` re-OCRs its output and calls `_residuals`, which asks `detector.verify` for leftovers.
1. The drawn placeholder after a label (`password: Secret2`, `login: Name1`) matches the secret/username rule, so every image with such a line was refused. **Fixed** on branch `ws-img2` (commit in `../wt-img2`).
2. OCR garbles drawn email tokens (`Phone1_2lemail@example.com`, `email1@exampie.com`, `@examole`). **Partly fixed**: filter handles `example`/`examp[l1i]e`; variants like `@examole`, `@sxamalicpm`, `eraned4@npe.gile.com`, `адиинетаil3@example.com` still block `syn_invoice_*` images. Better approach: compare the OCR text against the *known drawn tokens* (re-identify a leftover as garbled token by fuzzy match to the set of tokens we drew, or strip the drawn token rectangles from the verify OCR) instead of regex whack-a-mole.
3. A real miss: a date on its own line after `born` (`09/01/1960`, `21/07/1984`) and a passport (`B29513614`) stay readable across 3 passes: the label and value are on different OCR lines, so neither view detects them as BIRTH_DATE/PASSPORT in the paint step, while `verify` (position-free rules) does. Fix idea: run the paint step on a joined view with the same position-free rules `verify` uses, so the painter can never be weaker than the checker.

After fix 1+2 (partial), `cm_jpg_en_041` produces a file; `syn_mail_ru_png_screenshot` ok; `syn_resume_ru_jpg_scan` attention (produced). Not yet re-run on the full image set.
